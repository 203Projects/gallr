## 1. Production guard: real mismatch, overstated standalone severity

Evidence: `scripts/production-cutover/assert-production-target.sh:327–345,710–723`. `SAFE_PATH` preserves the inherited PATH. An absolute `TRUSTED_NODE` is resolved from a fixed path **only in solo-operator mode**, and is used for the policy-window evaluator (`:118`). The final validator instead runs bare `node`, while passing `GALLR_PRODUCTION_VALIDATION_DATABASE_URL` in that child's environment. Reviewing/hashing the validator bytes does not attest this interpreter.

A local isolated probe extracted the exact four-line final environment/invocation block from the audited file and ran it with a temporary PATH-first `node` stub and a synthetic marker rather than a credential. The stub received the marker and returned success even though stdin contained JavaScript that would throw if interpreted. Output: `exact_final_invocation_stub_probe= 0 PATH_STUB_RECEIVED_SYNTHETIC_URI`.

**Prerequisites and counterevidence:** an adversary must make an executable resolve before the intended Node in the operator's actual PATH, and the operator must then run the credential-bearing workflow. Merely submitting catalogue content, an OAuth link, or a repository issue does not achieve this. Reviewed-commit checks, policy/manifest sealing, exact project linkage, and the clean-checkout gate at `:673–675` remain real obstacles to ordinary checkout tampering. The probe tests the final invocation only; it is not a demonstration of bypassing these complete gates. The guard performs local validation, not production mutation. Same-user host compromise often already permits credential interception through other tools, so the scan does not establish substantial new attacker authority.

**Fix:** select and consistently invoke an approved absolute interpreter in both governance modes; constrain the entire relevant toolchain and executable-directory permissions, not just the word `node`. An absolute path alone does not prevent replacement of an operator-writable installation. Add a full fixture regression asserting that a prepended Node stub cannot see the validation input or forge acceptance. Do not describe this as remote code execution or proof that production credentials have leaked.

## 2. Map stored XSS: highest-priority web fix, with publication prerequisites

Evidence: `web/map/index.html:95–97` embeds `mapData.island | dump | safe` inside an `application/json` script element. `web/_data/mapData.js:10–27` carries name, venue and address strings into the island. The map's later use of textContent cannot repair an HTML parser breakout occurring before JSON parsing. `web/scripts/fetch-exhibitions.js:102–107` preserves original row strings during enrichment; writing JSON to disk does not make their later raw HTML inclusion safe.

The payload shape `</script><script>…</script>` is enough to terminate the JSON element. A local HTML-parser probe produced two script elements with ordinary JSON serialization and one when `<` was encoded as `\u003c`. This is a parser-context regression proof, **not an execution of the real Nunjucks build or a browser exploit**; the checkout has no local Nunjucks/Playwright dependencies installed. No production site was loaded.

**Later migrations checked:** the scan cites the original owner validator in `20260731143000_gallery_owner_publishing_loop.sql:280–340`. Its replacement in **`20260805125752_gallery_info.sql:675–734` still validates text types/lengths, not HTML/script safety**, and now also permits paired coordinates. `20260831020202_explainable_art_metadata.sql:517–547` renames that validator and delegates ordinary fields to it after removing art-metadata keys; it does not sanitize names or venues. Therefore the later SQL does not invalidate the finding.

**Prerequisites/limits:** a gallery owner cannot directly publish. `20260721051120_admin_command_api.sql:917–919` requires publisher authority, with revision/required-field checks at `:965–984`. A crafted draft must be approved (or originate from a malicious/compromised publisher), included in a subsequent web build, remain non-closed, and have finite coordinates to enter the map island. The deployment must also consume the affected catalogue: `web/scripts/lib/exhibition-reader-source.js:13–40` supports canonical-v2 but defaults to legacy. A canonical owner draft's mere existence does not prove it reaches a deployed legacy-fed site; that would require the corresponding publication/mirroring path. This operational setting was not inspected. No CSP was found in the searched source configuration, but CDN/header settings remain unverified.

The impact established is public-origin script execution and access to origin-readable state. It is **not** established theft of administrator credentials on a separate origin, server execution, or bypass of publication approval. Also, the owner patch allowlist does not directly allow `slug`; controllable name/venue/address fields are sufficient, so slug control is unnecessary to the claim.

**Fix:** provide a dedicated script-safe JSON serializer that encodes at least `<` (optionally also `>`, `&`, U+2028/U+2029), and emit only that trusted serializer's output without generic raw-JSON assumptions. Simply removing `safe` and HTML-escaping JSON is not necessarily a working replacement inside a script raw-text element. Add real template/browser regression tests for mixed-case closing tags and ordinary Unicode data; use CSP as defense in depth. Approval should not be expected to recognize executable strings.

## 3. OAuth callback: normal code flow does not protect the implicit fallback

Evidence: `shared/src/commonMain/kotlin/com/gallr/shared/data/network/SupabaseProvider.kt:104–145`. A callback containing `code` goes to `exchangeCodeForSession`; otherwise fragment `access_token` and `refresh_token` values go straight to `importSession`. No shared-handler exact URI validation, pending-login requirement, state binding, or user confirmation protects this latter path.

Reachability is explicit: Android's exported singleTask activity has a browsable `com.gallr.app://login-callback` filter (`androidApp/src/main/AndroidManifest.xml:36–50`); both warm intent and cold launch forward URI strings (`MainActivity.kt:95–103,306–311`). iOS forwards open URLs (`iosApp/iosApp/iOSApp.swift:50–55`). The Android implicit-intent filter narrows routing but does not bind a request to a login initiated on this device. The finding does not need a mismatched URI: a correctly routed callback carrying the attacker's valid tokens suffices.

**Actual attack:** an attacker supplies a valid session for the attacker's own account, and induces delivery/opening of the callback on the victim device. Subsequent victim actions may be associated with that account. This is login CSRF/account confusion; it does not obtain the victim's original tokens, grant the attacker's account higher privileges, or defeat backend RLS. Arbitrary garbage tokens are not demonstrated to work. Real Supabase SDK/server import behavior and OS dispatch were not exercised, so the conclusion is source-supported with a valid-token prerequisite, not a live takeover reproduction.

**Fix:** remove implicit fragment imports if no longer required; retain code-based exchange bound to a locally pending, single-use transaction and exact callback URI. Verify SDK-provided transaction binding rather than assuming any code branch is sufficient. Add no-pending-login, already-signed-in, replay, wrong-URI, and fragment-token tests with a fake auth adapter. Prioritize this above the local toolchain issue because the attacker starts outside the victim device's trusted execution environment.

## 4. Bookmark cache: newer account archive isolation does not cover bookmarks

Evidence: `CloudBookmarkRepository.kt:14–24` has one identity-free MutableStateFlow. `SyncBookmarkRepository.kt:41–47` switches all authenticated users onto that same flow; refresh only changes it after a successful query, while retry exhaustion at `:125–139` leaves its contents untouched. Both platform constructors instantiate the repository outside individual account sessions.

`composeApp/.../App.kt:251–275` activates/deactivates the newer My Gallr account coordinator and migrates/refreshes bookmarks after authentication. **That guard is real but distinct:** `shared/.../MyGallrAccountSync.kt:119–148` keys the visits/follows account archive by user and clears its active identity on deactivation. It does not invalidate CloudBookmarkRepository. `AuthRepositoryImpl.kt:104–115` only signs out or clears the auth session following server-confirmed deletion.

Account A's IDs can therefore be shown under B in the same repository lifetime before B's fetch completes, and remain on repeated failure. Guest routing uses the local store, so this is not a claim that every anonymous screen always shows A's cloud data. A process restart or successful refresh reduces exposure. Backend RLS is not bypassed; no remote enumeration of A's bookmarks was shown. `clearAll()` is a server-deletion operation, not an appropriate cache-only logout fix.

**Fix:** key the cache by stable user ID or synchronously reset to an empty/loading state on every identity transition; use generation checks/cancellation for late asynchronous results. Cover A→guest→B, direct A→B (including OAuth session replacement), deletion, failed refresh, and delayed A responses with local tests. Combining this with OAuth can display stale A state while authenticated as the attacker, but automatic remote exfiltration of that stale set was not proven.

## 5. Push lifecycle: server guards prevent takeover, not post-logout delivery

Evidence: `App.kt:460–478` only enables current followed-gallery subscriptions. Sign-out/deletion callbacks at `:1287–1293` have no inverse revocation. `GalleryAlertRegistrationRepositoryImpl.kt:15–17,41–55,84–155` persists installation identity/secret and supports individual enable/disable, not account teardown or credential rotation.

**Later migration checked:** `20260829065400_bound_gallery_alert_enrollment.sql:327–341` rejects cross-account rebinding when both IDs are non-NULL and preserves the old binding through `coalesce`. This reduces takeover risk but can leave B unable to use A's installation after logout. It does not revoke A's subscriptions. The same migration's current fan-out at `:593–603` checks enabled subscription, active token, and last_seen within 180 days; it does not require a live account session. Existing claimed jobs at `:657–663` again require an active token, not an owning authenticated user.

Deletion is materially different from logout: `20260814020000_gallery_alert_installation_commands.sql:12` declares `user_id ... on delete set null`, while subscriptions cascade only if the **installation** is deleted (`:27–34`). Thus identity deletion leaves the installation/token/subscriptions intact and unbinds the user instead of revoking delivery. The account-deletion migration `20260808110631_authenticated_account_deletion.sql` concerns authorization and avatar cleanup, not push teardown; no later replacement lifecycle cleanup was found. NULL-user installations also explain why post-deletion rebinding differs from logout's account conflict.

**Impact boundary:** public exhibition/gallery notification text can reveal the previous user's interests on the same device after logout/deletion, conditional on prior enrollment/permission, active push credentials, an enabled delivery pipeline and a qualifying publication event. No private message content or cross-device push-token theft was established. Enrollment quotas, installation-secret checks, revision guards and the activity window bound different risks; they do not enforce logout semantics. Anonymous device subscriptions may be intentional, but preserving account-derived follows after an account teardown should be an explicit policy, not accidental inheritance.

**Fix:** add atomic installation revocation that disables subscriptions, deactivates tokens, and prevents queued delivery; integrate it with account deletion server-side and logout/identity changes client-side. Clear or rotate local credentials and design offline cleanup/retry so local sign-out does not depend indefinitely on network success. Rotation alone leaves the old server token active and is not sufficient. Test queued jobs, offline sign-out, A→B, deletion followed by re-enrollment, and any deliberate anonymous-subscription exception.
