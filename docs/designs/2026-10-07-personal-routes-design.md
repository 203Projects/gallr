## Problem Statement

gallr generates 2–5 stop routes on device (neighbourhood, for-you, closing-soon, saved) and shows them on a map panel with a summary and stop list, but a route is never the visitor's own: the planner picks and orders the stops, nothing is persisted, and nothing can be sent to anyone. The founder wants a personal route: pick any exhibitions, give the route a name, drag stops into an order with the map and timing updating live, and share it the way an exhibition is shared today, with likes from other users later.

Founder's framing, verbatim: "everything is within gallr app so that this could be another reason why people log in to gallr app. however, it should be shareable content as well as exhibitions."

## Demand Evidence

None observed yet. The stated motive is a retention hypothesis ("another reason why people log in"), not a watched planning problem. The founder has not sat behind anyone planning a multi-show day or sending a share card (D5: "Not yet"). The April 2026 social-layer design recorded that opinions already travel through Instagram stories, Naver blog and KakaoTalk, which is where a route link would travel too. Treat recipient behaviour on shared routes as the number that decides whether routes deserve more engineering.

## Status Quo

Not described in this session; the founder answered the status-quo question with the retention motive above. The assumed workaround for a gallery day in Seoul is a KakaoTalk thread of links plus pins in Naver or Kakao Map, with order and timing in someone's head. This is an assumption until someone is watched (see The Assignment).

## Target User & Narrowest Wedge

- **Target user:** a gallr visitor who has saved or visited several current shows and wants to send a friend a day: which shows, in what order, and whether it works with today's hours. They sign in at save or share, not before.
- **Wedge (D4, decision 7e4420eb):** compose any current or upcoming exhibitions, name the route, drag to reorder with the map and timing recomputed on device, share as a PNG card and a public gallrmap.com page. Likes, author profiles and a routes feed are deferred until a discovery surface exists.
- **Not the wedge:** saving the planner's own route (the machine's order carries no taste); image-only export without login (nothing to keep or like).

## Constraints

- Shared-first and test-first (constitution): all route evaluation, draft and persistence logic in `shared/commonMain`; ViewModels and Compose UI in `composeApp/commonMain`; tests before implementation.
- DESIGN.md: monochrome, 0dp corners, one accent (`ctaPrimary`, `activeIndicator`, `interactionFeedback` only), Inter + Gothic A1, 8pt grid, bilingual inline copy, functional motion only. Drag feedback must be colour or opacity, not decorative movement.
- One Supabase identity plane; new tables use server-owned RLS; migrations follow the production-recorded lineage (validator first, pgTAP suites).
- gallrmap.com is an Eleventy static site on Vercel, deployed on merge and by a daily rebuild workflow through a deploy hook; a per-route page cannot be a rebuild. KakaoTalk link previews read Open Graph tags from the served HTML.
- The on-device planner (`NeighborhoodRoutePlanner`) selects and optimises stops; it must not be called on a user-ordered route, because it would re-sort.
- Route names are user content: same policy as Thoughts (auto-publish, admin revoke).

## Premises (agreed D7, premise 1 revised D9)

1. A route is authored. Composing needs no account; sign-in is requested at save or share, like local-first bookmarks (decision f0daf22e). Anyone with the link reads a route without an account.
2. Reader first. The shared route page (web now, in-app later) is useful alone: map, ordered stops, today's hours, walking times, one Start button. Sharing is by link and card into KakaoTalk, as for an exhibition.
3. The author's order is authoritative. Reordering recomputes timing and the map on device and flags hours conflicts on the affected stop; it never re-sorts.
4. Likes, author profiles and a routes feed wait for a discovery surface.
5. Routes persist in Supabase under the existing identity plane: owner writes, public read for published routes, no new auth.
6. The public route page is served, not rebuilt: an Edge Function returns HTML with Open Graph tags and the route data; the static site routes `/route/:id` to it.

## Landscape

- Drag-and-drop itinerary editors with a map are table stakes (Wanderlog, Itini, iTineasy, TripShare). They do not know whether a route works today.
- Ex-Twitter staff on Lists: far more people want to consume a curated set than build one; Lists never moved engagement because the UX served creators. Google Maps retired public lists on profiles and kept share-by-link. Foursquare lists faded.
- Layer 3 (logged): build the reader's object first. A shared route is a startable planner output with order, hours and map, sent by link into KakaoTalk; likes and a feed wait for a discovery surface. gallr's closed catalogue with hours and an on-device evaluator is what no itinerary app has.

## Approaches Considered

- **A: Keep and send the planner's route** (name, up/down reorder, link share, reader page; ~1.5 weeks human / ~1 day CC; 5/10). Ruled out: the route starts as the machine's pick, so the taste that makes sharing worth it is thin. Fallback if B slips.
- **C: B plus in-app reader, profile routes, likes schema** (~6 weeks / ~5–6 days CC, including the hours-parser port; 10/10). Ruled out for v1: universal links, profile routes and a hidden likes table are work before any route has been opened by a stranger.

### Approach B: Composer with live evaluation, card and page (CHOSEN, decision 1ba4b59b)

~3–4 weeks human / ~3–4 days CC (revised for the hours-parser port and the Admin revoke action); completeness 8/10. The author picks, names and orders; a new shared evaluator keeps that order honest; the share card and a served public page mirror exhibition sharing.

### Shared (`shared/commonMain`, package `com.gallr.shared.route`)

- `PersonalRoute(id: String?, name, stops: List<PersonalRouteStop>, authorId: String?, isPublished: Boolean, updatedAt)` with invariants: 2–10 stops, distinct exhibition ids, name 1–60 characters after trim (the app trims before save; the database checks the trimmed value). `PersonalRouteStop(exhibitionId, snapshot: nameKo, nameEn, venueNameKo, venueNameEn, latitude, longitude)`: the snapshot is copied at save time so a stop still renders after its exhibition ends or is unpublished. Routes carry no visit date in v1: the public page evaluates today in Asia/Seoul; the composer evaluates the reference day defined by `RouteEvaluator` (today, or the next day the first stop opens when today cannot be walked).
- `RouteEvaluator.evaluate(stops in author order, exhibitions by id, origin: GeoPoint?, today, now: LocalTime, legEstimator): PersonalRouteEvaluation`. Reuses `parseOpeningHours`, `RouteLegEstimator`, the planner's default visit minutes per stop, the departure-shift rule (leave so the first stop is reached as it opens) and `RouteStopSchedule`. Origin is the device location when permitted, otherwise stop 1 (then no departure line). **Reference time (committed):** the day plan is anchored at the later of now and the first stop's opening today; once now is past the first stop's closing time today, or the first stop is closed today, the evaluator plans the next calendar day on which the first stop opens, from that opening, and the summary line names the first stop's opening on that day (내일 11:00 개관 기준, or the weekday); the departure line, when an origin exists, gives the time to leave, and with a stop-1 origin there is no departure line. The rollover search is bounded to seven calendar days and never passes the first stop's exhibition end date; when no opening is found the evaluator plans today and flags the stop. When the first stop has no usable hours, has ended or is unavailable, the evaluator anchors at now, performs no rollover, flags that stop as the first conflict and omits the reference-day label. An evening composer therefore never shows a day that cannot be walked, and the public page's "today" flags remain a separate, simpler view. Unlike the planner it never reorders or drops a stop: each stop gets a `RouteStopVerdict` of Open, ClosedOnPlannedDay, ArrivesAfterClose, VisitCutShort(minutes), Ended, Unavailable (exhibition no longer published; rendered from the snapshot) or HoursUnknown, and the summary carries totals plus the first conflict. Pure function with fixed-clock tests on the published-catalogue fixture: before the first stop opens (anchor at opening, departure line present), mid-day (anchor at now), after close (rollover to tomorrow's opening with the 내일 label), first stop closed today (rollover to the named weekday), first stop with unknown hours, ended or unavailable (no rollover), a first stop whose exhibition ends before its next opening (no rollover, flagged), and a clock just before and just after midnight KST.
- **State model (committed behaviour).** The composer always works on one local draft (DataStore) that survives restarts and carries the remote id once the route has been saved. 저장 persists the draft's name and stops for the owner, asking for sign-in first if signed out; the first save creates the route unpublished and later saves replace name and stops only, never `is_published`; the draft stays as the working copy. 공유 always saves the draft's current edits first (the same `save_personal_route` call), publishes if the route is not yet published (sign-in if needed), then opens the share sheet with the card and link; a link is only ever produced for a published route whose saved state equals what the card shows, so a shared link is never dead or stale. Sharing from the 내 동선 list publishes the route if it is not yet published and then opens the share sheet; if the open draft is that route with unsaved edits, the list share runs the same save-then-share sequence. A failed save (offline, or any RPC error) aborts the share with an inline error and keeps the draft; a revoked-route rejection tells the author the route was removed and clears the draft's remote id so it can be saved as a new route. A published route stays editable: every save replaces its stops in one transaction (below), so readers only ever see a complete route, old or new. "새 동선" and opening a saved route from the list both replace the draft slot, each after a confirm when the current draft has unsaved edits.
- `PersonalRouteDraftRepository` (DataStore, local-first): the single draft described above.
- `PersonalRouteRepository` (supabase-kt calling the RPCs below, `Result<T>` boundary like catalogue repositories): `saveRoute`, `publishRoute`, `listMine`, `loadMine(id)`, `deleteRoute`. Public read is not needed on mobile in v1 (the reader is the web page).
- "내 동선" list: a section of the Map tab's route sheet listing the owner's saved routes (name, stop count, published state) with open, share and delete. Without it a saved route would be reachable only through its own share link.
- Share model: `PersonalRouteShare(url = "https://gallrmap.com/route/{id}?s=share", cardTitle, stopCount, totalMinutes)`; the author's own preview opens the page without `?s=share` (see analytics).

### Supabase

- Migration (lineage validator first): `personal_routes` (id uuid pk default gen_random_uuid, owner uuid not null references auth.users on delete cascade, name text check (char_length(btrim(name)) between 1 and 60), is_published boolean default false, revoked_at timestamptz null, created_at, updated_at) and `personal_route_stops` (route_id references personal_routes on delete cascade, position smallint, exhibition_id uuid (the canonical exhibition id, no foreign key so a stop survives catalogue edits), name_ko, name_en, venue_name_ko, venue_name_en, latitude, longitude, primary key (route_id, position)).
- **Writes go through RPCs, never direct table writes.** `save_personal_route(id uuid null, name text, stops jsonb) returns uuid` (SECURITY DEFINER, raises when `auth.uid()` is null, checks the caller is the owner or creates the route for the caller, rejects when `revoked_at` is set, enforces 2–10 distinct stops, and deletes-then-inserts the stops inside its own transaction so a reorder never leaves a partial route); `publish_personal_route(id)` (owner, refuses revoked); `delete_personal_route(id)` (owner). Every owner RPC raises when `auth.uid()` is null, and EXECUTE on all route RPCs is granted to `authenticated` only (revoked from `public` and `anon`). Owners have select on their own rows and no insert, update or delete policies, so `revoked_at` and `is_published` cannot be changed except through the RPCs. `revoke_personal_route(id)` is a staff-only RPC: it requires `auth.uid()` to be present in the staff membership relation and raises otherwise, so it cannot be run from the SQL editor's postgres session. The v1 operator path is a small action in the Admin workspace, in the same moderation area as the Thoughts revoke (the staff repository in `admin/src/repositories/`): "Revoke route by id" calls the RPC with the staff member's session. The Admin change carries its own typecheck, Vitest and build gate and its own deploy (see Distribution). pgTAP covers a staff caller succeeding, a non-staff caller and an anonymous caller being refused.
- RLS for readers: anonymous and authenticated select on `personal_routes` where `is_published and revoked_at is null`, and on `personal_route_stops` where the parent route satisfies the same condition. pgTAP covers: owner can read own unpublished route, stranger cannot; published route readable, revoked route not; owner cannot update `revoked_at` or `is_published` directly; `save_personal_route` rejects 1 or 11 stops, duplicates, an untrimmed-over-length name, and a revoked route; `publish_personal_route` rejects a revoked route; anonymous calls to save, publish and delete are rejected; a reorder is atomic.
- Edge Function `public-route` (Deno, `deno.json`, README like `record-exhibition-view`): **renders the complete page server-side.** `GET /route/{id}` returns HTML that links the site's two unhashed stylesheets by URL (`https://gallrmap.com/styles/tokens.css` and `/styles/main.css`, whose presence in `dist/styles/` the web test suite asserts), carries per-route Open Graph tags (name, "N stops · ~X km", `og:image` = the cover of the first stop whose exhibition is still published and has a cover, else the site's default Open Graph image; a raster the scrapers accept, with a route-shaped preview deferred because scrapers do not render SVG), draws the map as an inline monochrome SVG of numbered stops joined by a line on a blank grid (no tiles, no MapLibre), and lists the stops. `?format=json` returns the same data for the in-app reader slice later. Reads, all with the service key, so RLS does not apply and the filters `is_published and revoked_at is null` are the function's own contract, covered by `deno task test` 404 cases for an unpublished and a revoked route: the route and its stop snapshots, the currently published canonical exhibitions for those ids (hours and current names when still published; a missing one renders from the snapshot as 더 이상 볼 수 없는 전시 without a link, an ended one as 종료 with its dates), and `profiles.display_name` for the author through the service key, since publishing a route makes the author's display name public exactly as a Thought does. Missing, unpublished and revoked routes all return the same 404 page with neutral Open Graph tags. Language from `?lang` or `Accept-Language`, Korean default.
- **The hours logic is ported, deliberately and narrowly.** The function needs only: the opening-hours parser (TypeScript port of `parseOpeningHours`, tested against the 21 golden cases in `specs/088-discovery-accuracy-fixes/contracts/opening-hours-grammar.md` as a parity test in `deno task test`), today's open or closed verdict per stop in Asia/Seoul (fixed-clock test around midnight), and straight-line walking estimates with the app's circuity factor. The departure shift and the visit-by-visit schedule are not ported: the page shows per-stop hours and walking times, the composer shows the full timing. The estimate rises by about a day of CC time for the port and its parity test (approach B becomes ~3 to 4 days CC).
- Analytics (072 aggregate pipeline, no author or reader identity): `route_draft_started` (composer opened with a new draft), `route_published`, `route_shared` (share sheet opened), `route_opened` sent by the page's client script, never on the HTML fetch, with known scraper user agents excluded and the link's `?s=share` recorded as an aggregate dimension so author previews (no parameter) are separable; `route_started` on the Start tap. Both web events post to a new Edge Function `record-route-event` modelled on `record-exhibition-view` (POST, bounded body, daily aggregate by route id and share flag), whose allowed origins include gallrmap.com and the function origin used by the fallback link.

### Web (`web/`)

- `web/vercel.json` gains a rewrite from `/route/:id` to the `public-route` function URL (Vercel rewrites accept absolute external destinations), so KakaoTalk, Instagram and iMessage scrapers see per-route Open Graph tags from the served HTML. The function must not inherit `record-exhibition-view`'s exact-Origin requirement, because scraper GETs carry no Origin header. Fallback if the rewrite fails verification: shared links point at the function URL directly.
- No Eleventy template is involved for route pages: the function serves the whole page and reuses the site's stylesheet by URL. The page shows the route name, the author's display name, the inline SVG map, the stop list with today's hours and walking times, one Start button that opens stop 1 in the map app, and a single "gallr에서 열기" link (app store or app). "Copy to my routes" waits for the in-app reader slice.

### App (`composeApp/commonMain`)

- Share: a route variant of `SharePreviewScreen`'s card (monochrome map, name, stops, QR to the route URL) through the native share sheet, plus the link itself.
- Reduced motion and screen readers: drag handles remain buttons with "위로 / 아래로" actions, so reordering never depends on the gesture.

### R3-1 — consistency (blocking)

**Problem**

> The new committed reference-time rule has the composer plan the next calendar day on which the first stop opens whenever now is past the first stop's close or the first stop is closed today, but the model paragraph still commits 'Routes carry no visit date in v1: every surface evaluates for today in Asia/Seoul' and the App section still describes 'the existing summary presentation evaluated for today with the departure line'. The verdict set in the same sentence keeps `ClosedToday` although the evaluated day may now be tomorrow or a later weekday. Two committed statements give different evaluation days for the composer, so an engineer following the model or App section implements today-only while the evaluator section requires the rollover.

**Remedy**

> Make the evaluated day consistent everywhere: reword the model invariant to 'the page evaluates today; the composer evaluates the reference day defined by RouteEvaluator (today, or the next day the first stop opens when today cannot be walked)', change the App section's 'evaluated for today' to 'evaluated for the reference day', and either rename `ClosedToday` to a day-neutral verdict (for example `ClosedOnPlannedDay`) or define it as closed on the evaluated day.

### R3-2 — completeness (blocking)

**Problem**

> The anchoring and rollover rule is keyed entirely to the first stop's opening and closing times, yet the same sentence lists HoursUnknown, Ended and Unavailable as verdicts any stop, including the first, can carry, and the evaluator 'never reorders or drops a stop'. For a first stop with unparseable hours, an ended exhibition or an unpublished one there is no 'opening today' and no 'next calendar day on which the first stop opens', so the anchor, the rollover and the summary label are undefined. The forward search for the next opening day also has no stated bound: a first stop whose parsed hours yield no open weekday, or whose exhibition ends before its next opening day, never terminates it. These are inputs the published-catalogue fixture will contain, so the committed rule is incomplete for cases the composer will meet on its first walkthrough.

**Remedy**

> State the anchor when the first stop has no usable hours or is Ended/Unavailable (for example: anchor at now, perform no rollover, flag that stop as the first conflict, and omit the reference-day label), bound the rollover search (for example at most 7 calendar days and never past the first stop's exhibition end date, otherwise evaluate today and flag), and add these cases to the evaluator's fixed-clock tests.

### R3-3 — completeness (minor)

**Problem**

> The reference-time rule now has three branches (before opening, during hours, after close or closed today with rollover) plus the midnight boundary in Asia/Seoul, but the test sentence is still the generic 'fixed-clock tests on the published-catalogue fixture'; the round-2 remedy's named clock cases were not carried into the document, so the test obligation for the new behaviour is implicit.

**Remedy**

> Name the evaluator test cases for the reference time: before the first stop opens (anchor at opening, departure line), mid-day (anchor at now), after close (rollover to tomorrow's opening with the 내일 label), first stop closed today (rollover to the named weekday), and a time just before and just after midnight KST.

**Remedy**

### Amended plan summary (what spec 089 should implement)

The approved design above stands except where the decision ledger changes it:

- **Route page host (D1, D2, D13, D16, D19).** `/route/{id}` is served by a Vercel Function in `web/` through an internal rewrite, reading with the publishable key under row-level security. The route row and its ordered stops are read in one embedded request. Successful pages cache for 60 seconds with 60 seconds of stale-while-revalidate; a read failure returns a 503 error page with `no-store`, never the 404 page. Links are `/route/{id}?s=share&v={revision}`. The same function receives the page's events at its own path. The Supabase `public-route` function, its fallback link and `record-route-event` are dropped.
- **Shared code (D3, D15).** The planner's private schedule becomes one internal timeline in `com.gallr.shared.map`. `RouteEvaluator` adds run-date checks and a `NotYetOpen(openingDate)` verdict.
- **Database (D4, D5, D7, D12, D14, D17, D18).** The app sends ordered exhibition ids under an app-chosen route uuid. `save_personal_route` locks the route row, copies snapshots from `exhibition_catalog_v2`, keeps a no-longer-published stop only if the route already holds it, returns a distinct error naming blocked stops otherwise, and returns the stored route. `personal_routes.published_at` is set on first publish. `record_route_page_event` records `route_page_opened` and `route_page_started`. `revoke_personal_route` is called from a new Admin page at admin.gallrmap.com.
- **App (D8, D9, D16, D18).** A route ApiClient (Ktor, bearer token) sits behind `PersonalRouteRepository`. The draft stores the owner's account id and detaches on mismatch. `PersonalRouteComposerViewModel` and `MyRoutesViewModel` share one save-then-publish-then-share step. The share card is drawn from the save response.
- **Analytics (D6, D14).** The three author events join the 072 pipeline and read as unavailable until 072 is activated. The recipient loop is computed from `published_at` and the daily page counts, labelled unauthenticated traffic.
- **Tests (D10, D11).** One JSON parity file checks the Kotlin and JavaScript hours readers. The targeted regression contracts cover the planner, share card, analytics handler, web build and Map route sheet.
- **Distribution order (amends the Distribution Plan).** Migration (lineage validator, pgTAP, concurrency script), then the Admin deploy with the revoke page, then the web deploy with the Vercel Function and rewrite plus a preview-deploy scraper check, then the mobile release.
